# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`drupilot` is **not an application** — it is a **Claude Code plugin** that ports Drupal 9/10 modules and themes to Drupal 11. There is no build step, package manager, or compiled output: the plugin is composed of markdown (commands, agents, skills), JSON (manifests, config, hooks) and a Bash script library. End-user documentation lives in `README.md` (English) / `README_es.md` (Spanish translation). The authoritative product spec is `../PROMPT.md` — its §1 carries verified (June 2026) ecosystem versions and toolchain commands; treat those as facts rather than re-researching.

## Language convention (important — overrides PROMPT.md)

All **functional content** of the plugin is **English only**: comments, log lines, user-facing messages, prompts, reports, frontmatter `description` fields. `PROMPT.md` §0/§7 specifies Spanish output, but that was **explicitly reversed by the user**. The single exception is `README_es.md`, the Spanish translation of `README.md` — if you change `README.md`, mirror it there. Never reintroduce Spanish into any other file. Code identifiers, package names and shell commands stay in their original form.

## Developing / validating the plugin

There is no test runner for the plugin's behavior, but there is **one local developer gate** — run it before every commit:

```bash
bash scripts/dev/check.sh            # all gates; exit 0 ok / 1 a gate failed
bash scripts/dev/check.sh --json     # per-gate {name,status,detail,findings} on stdout
bash scripts/dev/check.sh --only shellcheck,bang-lint   # or --skip ...
bash scripts/dev/check.sh --allow-known   # report the failures already tracked in its KNOWN_FAILING list without failing
```

Gates: `validate` (`claude plugin validate .`), `syntax` (`bash -n` on `scripts/*/*.sh` + `hooks/scripts/*.sh`), `exec-bit` (those scripts must be executable — git mode `100755`), `shellcheck` (`-S warning`, configured by `.shellcheckrc`; no check is disabled globally — intentional exceptions are inline `# shellcheck disable=SCxxxx  # reason`), `portability` (no bash 4-only or GNU-only construct in those scripts — see the bash 3.2 convention below; a line can opt out with a trailing `# portability-ok` and a reason), `special-vars` (no script assigns/declares/reads into/loops over a bash special variable such as `GROUPS`, `RANDOM`, `SECONDS`, `UID`, `PWD`, `BASH_SOURCE` — bash silently ignores or overrides it; opt out with `# special-var-ok` and a reason), `bang-lint` (no `<placeholder>` inside a ``!`...` `` exec span in `commands/*.md`, `skills/*/SKILL.md`, `agents/*.md`), `templates` (every `templates/*.tmpl` rendered with dummy values; XML outputs must pass `xmllint --noout`) and `json` (`jq empty` on `config/`, `hooks/`, `.claude-plugin/` JSON). A missing optional tool (`claude`, `shellcheck`, `xmllint`) is a skip, or a failure with `--ci`. It is bash 3.2-compatible, read-only, and never writes to the tree. Add a gate there rather than a parallel script.

A ``!`...` `` line in a command/skill/agent runs at command load, **before** the model sees it: it must be fully resolvable from `$1`/`$ARGUMENTS`/env. Anything that needs a `<placeholder>` must be written as an instruction for the model to run (a fenced block or a `!bash ...` line without backticks). `bang-lint` enforces this.

Smoke-test a script directly (set `CLAUDE_PLUGIN_ROOT` so path/config resolution works outside an installed plugin):

```bash
export CLAUDE_PLUGIN_ROOT="$PWD"
bash scripts/env/preflight.sh --profile all          # human report
bash scripts/env/preflight.sh --profile setup --json # JSON + exit-code gate (0 ok / 2 missing hard req)
bash scripts/env/detect-php.sh --json
```

Most scripts support `-h/--help`, validate their args (clean English error + non-zero exit on misuse), and have a `--json` and/or `--dry-run` mode.

To exercise the plugin end-to-end, install it locally: `/plugin marketplace add .` then `/plugin install drupilot@drupilot`, and start a new session (hooks load at SessionStart).

## Architecture — how the pieces compose

The flow is **command → (gate) → skill + subagent → scripts → templates**, all reading one config and one shell library.

- **`scripts/lib/common.sh` is the contract everything depends on.** Every script sources it (group scripts via `../lib/common.sh`; hook scripts via `../../scripts/lib/common.sh`). It provides logging (`log_info/ok/warn/err/step`, `die`), tool/version detection (`have_cmd`, `tool_version`, `version_ge`, `docker_daemon_up`, `ddev_running` — read-only via `ddev describe`, never starts a project — and `ddev_ensure_running` for the toolchain-running scripts that may start it explicitly), `print_usage` (the shared `-h/--help` printer: the header block only), `run_with_timeout`, config access, subject detection (`find_drupal_root`, `subject_type`, `subject_machine_name`, ...), the path/cache helpers (note the split: `project_state_dir` is the HIDDEN per-project machine state under `$HOME` — `assess.json`/`last-test.json`/the lockfile, kept out of the tree so it survives `git clean` and never leaks; `project_artifacts_dir` is the VISIBLE, gitignored `<root>/.drupilot/` for human-facing outputs — `port-report.md`/`viability-report.md`/coverage/the local patch), the **determinism/lockfile helpers** (`deterministic_mode`, `lock_get`/`lock_set`/`lock_set_json`, `lock_resolve`, `lock_show`/`lock_clear`, `drupilot_lock_file`), the **interaction helpers** (`confirm`, `choose_one`, `tty_readable`, `announce_patch`), the **prefs helpers** (`drupilot_prefs_file`, `prefs_set`, `config_enum`), the **portability helpers** (`lc`, `sed_inplace`), the **core/test-toolchain helpers** (`drupal_core_version`, `core_dev_requirement` — the `drupal/core-dev` requirement matched to the installed core —, `phpunit_available`) the **DDEV add-on readers** (`ddev_addons_installed`, `ddev_addon_version`) and the **toolchain-health helpers** (`rector_smoke`, `rector_output_ok`/`rector_error_excerpt` — the one Rector crash detector —, `toolchain_diagnostics`, `toolchain_reference_version`, `installed_package_version`, plus `phpstan_extension_config_problem` — a broken phpstan/extension-installer `GeneratedConfig.php` —), the **DDEV exec helpers** `ddev_global_composer` (name the container's own Composer by absolute path whenever `composer` is not the first word of a `ddev exec` command line — under `timeout`/`sh -c` a bare `composer` resolves to the test-bed's `vendor/bin/composer`) and `run_dropping_ddev_failure_line`, and the **per-subject state helpers** (`subject_state_file` → hidden `<state_dir>/state.json`, `state_get`/`state_set`/`state_set_json`, `stage_rank`, `phase_record`/`phase_get`/`phase_reached`: the monotonic `stage` + `stages{}` record that `port-report.sh` (ported/refactored, from the manifest phase) and a verified whole-suite `run-phpunit.sh` (tested) write and `next-step.sh`/the post-edit hook read; it keeps the legacy `phase` marker in sync; `DRUPILOT_STATE_FORCE` allows lowering it). **Do not reinvent these in individual scripts.**

- **stdout/stderr discipline:** all `log_*` output goes to **stderr**; **stdout is reserved for parseable payloads** (JSON, file lists). Anything a command parses from a script comes from stdout. The analysis scripts (`run-rector.sh`/`run-phpstan.sh`/`run-phpcs.sh`) expose a `--json` mode for a reproducible, machine-readable verdict (native `--error-format=json`/`--report=json`; a `{changed_files,...}` summary for Rector).

- **Config resolution (`config/defaults.json` + `config_get`):** resolution order is **env var > per-project `.drupilot.json` > `config/defaults.json` > caller default** — the env var always wins. The `.drupilot.json` tier lives at the Drupal ROOT and is where in-flow **tabbed choices** are remembered (`prefs_set` writes it; gitignored via `ensure-gitignore.sh` so it never lands in a patch). `config_enum` validates a closed-set key (used non-fatally in `preflight.sh`); a tabbed choice can also be pre-answered with `DRUPILOT_CHOICE_<KEY>`. `DRUPILOT_PHP_TARGET` (default `8.3`) drives all tuning (Rector php sets, PHPStan level, PHPCS, DDEV `php_version`); read it via `resolve_php_target`, never hardcode a version. Versions flagged uncertain (notably PHP 8.5) are gated through `php_target_unconfirmed` and detected at runtime — never assumed.

- **Determinism + lockfile (`DRUPILOT_DETERMINISTIC`, default `true`):** ports are reproducible by default. The resolved Drupal core, dev toolchain, digests commit SHA and DDEV add-ons are frozen in a per-project `drupilot-lock.json` and reused on later runs via the `lock_resolve` *resolve-and-freeze* pattern; `DRUPILOT_DETERMINISTIC=false` resolves fresh and refreshes the lock. **The lock is keyed by the Drupal ROOT** (the only path every context knows), so it lives in a different state dir than `assess.json`/`last-test.json` (keyed by the subject) — readers derive it via `DRUPILOT_PROJECT_DIR=$ROOT drupilot_lock_file` (`assess.json`/`last-test.json` are keyed by the subject instead). `scripts/env/lock-sync.sh` captures/refreshes it (reads `composer.lock` + `ddev add-on list`; called by `ddev-up.sh` and `ddev-add-ons.sh`); `lock_show`/`lock_clear` let a developer inspect or reset it, and `/drupilot-status` prints it. Toolchain constraints in `defaults.json` stay at the verified PROMPT §1 ranges; the lock pins the exact patch. The dev toolchain is installed only by `scripts/env/install-toolchain.sh`, which pins the lock when it holds the whole known-good set, else the shipped **known-good reference** `config/toolchain-reference.json` (`DRUPILOT_TOOLCHAIN_SOURCE`), smoke-tests it (exit 3 = installed but broken) and re-syncs the lock. Never invent patch versions: a version enters `toolchain-reference.json` only after it was installed and verified together in a DDEV test-bed.

- **`scripts/env/preflight.sh` is the requirements gate engine**, reused three ways: the `/drupilot-doctor` command, the SessionStart hook, and a per-command gate. It validates only what a profile needs (`analyze` → git+jq+composer/php; `setup`/`test` → Docker+daemon+DDEV; `contribute` → git+SSH/PAT), prints a human table or `--json`, and exits `0` (ready) / `2` (a hard requirement is missing) — `profile=all` always exits 0. Commands call it first and abort with the actionable report and **no side effects** when it fails.

- **Host vs. DDEV execution (`drupal_runner`):** analysis/test scripts `cd` to the Drupal root and prefix toolchain calls with `$(drupal_runner)`, which yields `ddev exec` when the DDEV environment is up and an empty string (host `vendor/bin`) otherwise. `ddev_running` is read-only (never starts a project); scripts that run the toolchain start a stopped project with `ddev_ensure_running` — the analysis scripts (Rector/PHPStan/PHPCS, `analyze` profile, no Docker required) through `ddev_ensure_running_or_host`, which falls back to the host `vendor/bin` tool when DDEV cannot start. `run_with_timeout` does NOT propagate through `ddev exec`/`ddev composer` (only the host client dies): bound in-container work with the container's own `timeout`, or stop it with `ddev_stop_composer` before cleaning up. Relative paths like `web/modules/custom/foo` resolve identically inside the container and on the host — this is why scripts must cd to the root and use relative subject paths. A **loose** subject (a module/theme not yet under a Drupal root) is never scaffolded on top of: `scripts/env/resolve-workspace.sh` (a pure `--json` resolver, like `core-strategy.sh`) targets a sibling `<name>-d11` test-bed (or `DRUPILOT_WORKSPACE_DIR`) and `scripts/env/place-subject.sh` (idempotent, `--dry-run`, runs after `ddev-up.sh`) moves/symlinks/copies it under `web/{modules,themes,profiles}/custom/<name>` per `DRUPILOT_PLACEMENT` (`move`|`symlink`|`copy`, default `move`); a module already inside a Drupal root keeps its layout (back-compat). **Origin hygiene:** drupilot must leave the developer's origin repo clean — `place-subject.sh` snapshots it first (`scripts/env/origin-hygiene.sh --snapshot`, baseline in the hidden state dir keyed by the ROOT; `--check` is report-only and feeds the port report), a `copy` skips local-environment residue (`.ddev/`, `vendor/`, `.drupilot*`, `.phpstan-cache/`, `node_modules/`) and drops symlinks escaping the tree, and any drupilot file written INSIDE a (possibly nested) subject repo is hidden with `git_local_exclude` (the repo's local `.git/info/exclude`), never by editing its tracked `.gitignore` — a parent root's `.gitignore` does not cover a nested repo.

- **Hooks are fail-safe by contract** (`hooks/hooks.json` + `hooks/scripts/*.sh`): they read JSON on stdin, **never use `set -e`**, **never exit non-zero**, guard every optional tool with `|| true`, and act only by printing `{"hookSpecificOutput":{...}}` on stdout (fail-safe default = exit 0 with no JSON). `PreToolUse`/`guard-contrib.sh` returns `permissionDecision: "ask"` for outward-facing git push/MR commands in `semi` mode **and always when `DRUPILOT_AUTONOMOUS=true`** (the backstop enforcing "an autonomous run never pushes on its own", regardless of `DRUPILOT_CONTRIB_MODE`). It also returns `ask` for a `git commit` that skips the repository's hooks (`--no-verify` / `-n`, or `-c core.hooksPath=...`) while a `pre-commit` or `commit-msg` hook is active — in **every** contribution mode and in autonomous mode; `DRUPILOT_HOOKS_GUARD=off` disables it, and it never denies. Its parser scans the whole command as one buffer (quote state across lines, backslash-newline continuations, `git` must be the segment's command word), so a heredoc commit message or a continued flag line is still seen. `PostToolUse`/`post-edit-lint.sh` is **phase-aware** (Phase 1 surfaces compatibility ERRORS only) and controllable via `DRUPILOT_POST_EDIT_LINT` (`autofix`/`report`/`off`), and it reports when phpcbf modified a file; `SessionStart`/`session-detect-env.sh` honors `DRUPILOT_SESSION_CONTEXT` (`on`/`off`).

- **Two-phase porting philosophy:** Phase 1 (`/drupilot-port`, skill `minimal-port`) makes the code D11-compatible with the smallest diff, preserving original behavior; Phase 2 (`/drupilot-refactor`, skill `full-refactor`) is an opt-in "Drupal 11 way" rewrite — now **granular**: a multi-select of modernizations (attributes / DI / strict types / `final` / deprecation-removal) + a PHPStan level, persisted as `DRUPILOT_REFACTOR_SCOPE`. A viability assessment (`/drupilot-assess`) always runs first as a decision gate and still emits a staged plan even when effort is high. **Preservation gate:** the adapted test suite staying green is the evidence behavior is preserved (both phases). Test adaptations may change only a test's *form* (PHPUnit/Drupal API), never *what it verifies* — a behavioral failure is a production-code regression fixed in code, never a test relaxed to fake green. `run-phpunit.sh` persists the honest verdict to `last-test.json` as `preservation`: `verified` / `verified-partial` (some groups skipped) / `regression` / `not-verified-blocked` (tests exist but could not run — `blocked_reason`; a missing `vendor/bin/phpunit` is this, exit 2, never a regression) / `not-verified-no-tests` (no test in the selected `--type` scope; `subject_has_tests` tells it apart from a subject with none — drupilot does not fabricate tests in Phase 1) / `pre-existing-failures` (tests fail, but every failing test already failed in the pre-port baseline — `run-phpunit.sh --baseline`, taken by the port flow before Rector, `test-baseline.json` in the state dir — and none that passed before fails now; not green, listed in `baseline.pre_existing`) / `not-verified-unbaselined` (no regression, but a failing test the baseline never meaningfully ran — its group crashed, or the un-ported module could not even be installed on the D11 test-bed — is listed in `baseline.not_baselined`; never counted as pre-existing, exit 3). The record lists every executed test (`tests`, from PHPUnit's JUnit log); a group that executed no test is `empty`, never passed. **Negative controls:** every new test drupilot writes must be proven able to fail by `scripts/tests/negative-control.sh` (undo the guarded change → red, byte-identical restore → green; `effective`/`ineffective`/`error`), which runs PHPUnit with `--no-record` and stores results in `negative-controls.json`. PHPUnit comes from `drupal/core-dev`, installed at setup to match the installed core (`core_dev_requirement`). A per-port **report card** (`port-report.sh` → `port-report.md`, from a `port-manifest.json` the flow writes) records what changed and why. **Hard vs soft deprecations:** `classify-deprecations.sh` (PHPStan JSON/text in, `--json` out) calls a deprecation *hard* when it is removed in a major ≤ the target major (always fixed in Phase 1, the only kind that counts in the effort verdict) and *soft* when it is removed later (still works on every target-major core); soft ones follow `DRUPILOT_SOFT_DEPRECATIONS` (`report` default / `defer` / `fix`, the latter never breaking the declared core floor), and the `lifecycle` catalog in `config/deprecations.json` (replacement, `replacement_since`, effort) only grows with facts verified against core source.

- **Run modes of the `/drupilot` router** (an explicit mode word wins; otherwise the mode is **inferred from intent** — a natural-language port request like "port this to D11" runs the flow as `full`, a bare `/drupilot` or "what's next" just recommends): `next` summarizes + recommends one step (the exploratory default); `status` is read-only; `full` runs the whole pipeline **with** confirmations and leaves refactor/contribute opt-in; `auto` (≡ `DRUPILOT_AUTONOMOUS=true`) runs `setup→assess→port→refactor→test` **hands-off** — no initial confirmation, `DRUPILOT_GENERATE_RULES` treated as `auto`, and it **never** does anything outward-facing (no push/MR/contribute, even in `auto` contribution mode). `auto` only relaxes drupilot's own gates; the Claude Code permission mode still governs Bash/Edit/Write.

- **Decision points & interaction model:** the developer owns the consequential forks, surfaced as **tabbed choices** — `AskUserQuestion` in commands (it is in their `allowed-tools`), with `choose_one()` as the fail-safe shell fallback. The recommendation is the pre-selected default; the answer persists to `.drupilot.json` via `prefs_set`. Canonical forks: router intent (full/next/auto), the **core target** (`/drupilot-port`, from `core-strategy.sh --json`), the **PHP target** (`/drupilot-setup`), the **digests rules to apply** (participatory per-rule review, pre-flagging rules whose target API exceeds the kept floor), the **refactor scope** (`/drupilot-refactor` multi-select → `DRUPILOT_REFACTOR_SCOPE` + PHPStan level), the **end-of-stage "what next?"**, and contribute **mode/push**. Outward-facing options are conditioned on `autonomous=false`; an autonomous run presents no interactive tabs and resolves with safe defaults. The next-step ladder (`doctor→setup→assess→port→[refactor]→test→[contribute]`) lives in one place, `scripts/env/next-step.sh` (router + `/drupilot-status` call it from a load-time line with `--from-preflight`, so it reads readiness itself; never restate it in prose).

- **Two patch kinds, one script (`scripts/contrib/make-patch.sh`) — patch is decoupled from contribution:** `--local` writes an offline preview patch next to the module (git-only, no rebase, no `contribute` gate; new files captured via a throwaway `GIT_INDEX_FILE` so the real index is untouched; diffed against the fork point from `git_port_base_ref` — upstream if an ancestor, else the closest merge-base among remote branches/nearest tag, never a reverse diff of unrelated upstream history; hidden from `git status` via `git_local_exclude`) — emitted automatically at the end of port/refactor, and on demand via the first-class **`/drupilot-patch`** command (model-invocable, no gate). A bare `--local` is named `MODULE-port-to-drupal-11.patch`; `--local --issue ID [--comment N]` names it with the Drupal.org **issue-comment** convention (`MODULE-…-ISSUE-COMMENT.patch`) **while staying offline** — to attach to an issue and test now, contributing the MR later. The legacy/contribution mode rebases onto `origin/BASE` and **verifies the patch applies cleanly onto that base** (a **hard gate** — a non-applying patch is discarded and the script exits non-zero; the `--local` preview only warns), produced **always alongside the MR**. A companion `scripts/contrib/make-issue.sh` generates the paste-ready Drupal.org issue summary + recommended mandatory-field values (`DRUPILOT_ISSUE_*`) and the MR/issue comment (phase-aware via `--phase port|refactor`); `open-mr.sh --description-file` uses that comment as the MR description.

- **PHP floor vs. target compatibility (`scripts/analysis/detect-php-floor.sh` + `recommend_core_target`):** a heuristic scan classifies the PHP a module's code requires. It feeds two things: the composer `require.php` floor when keeping `^10 || ^11` (`DRUPILOT_REQUIRE_PHP_FLOOR`, default `detect`, widens it to the real floor, e.g. `>=8.1`, vs `target` which keeps `>=<target>`), and a `php_floor_target_compatible` verdict (false when the code uses a construct newer than the target). It is a cheap static signal, **not** authoritative — the test suite running on the target PHP inside DDEV is the real proof. A kept `^10 || ^11` is reported `declared-not-verified` (mirrors the preservation gate) until `scripts/analysis/verify-core-matrix.sh` (`DRUPILOT_VERIFY_CORES`) statically checks it — PHPStan + `php -l` against a cached reference Drupal 10 core built through `ddev exec composer` under `<root>/.drupilot/cores/` — and sets `d10_support` to `verified-static` (clean, including the declared floor minor), `verified-static-above-floor` (clean only on a newer 10.x — a `^10` leg resolves to the newest 10.x, so the 10.0 floor itself is not proven) or `failed`; the runtime is never exercised on Drupal 10. `make-issue.sh --d10-unverified` carries the matching "verify Drupal 10 compatibility" task into the issue.
- **Project PHPCS ruleset and git hooks:** `run-phpcs.sh` prefers the subject's own ruleset (`.phpcs.xml`, `phpcs.xml(.dist)`; `DRUPILOT_PHPCS_RULESET` = `auto`|`drupilot`|PATH) and records the resolution in the hidden state dir (`phpcs-ruleset.json`), which `port-report.sh` renders and the post-edit-lint hook reuses. An auto-detected ruleset PHPCS cannot load falls back to `Drupal,DrupalPractice` with a warning; an explicit PATH that cannot load exits 2 (never a silent fallback). `scripts/contrib/git-hooks.sh` detects a repository's commit hooks (GrumPHP, husky, lefthook, pre-commit, CaptainHook, `core.hooksPath`) and, with `--run-equivalents`, runs drupilot's equivalents of their tasks and records `hooks-substitution.json` (`pass`/`fail`/`not-runnable`; a phpcs run that fell back is `not-runnable`). Commits let the hooks run; `--no-verify` only when `all_green` is true, and the substitution is stated in the port report.

- **The `dbuytaert/drupal-digests` layer** is third-party, AI-generated, and **unlicensed**: it is cloned into a runtime cache (`digests_cache_dir`, under `${CLAUDE_PLUGIN_DATA}`) and referenced by path — **never vendored or committed**. It runs after official `drupal-rector`, always dry-run → review → apply → validate, and is filtered by the target `core_version_requirement` so it does not silently raise the minimum to 11.2+. Toggle with `DRUPILOT_USE_DIGESTS_RULES`. Its default ref stays `main`, but in deterministic mode `run-rector.sh` resolves `main` to a commit SHA, **freezes it in the lockfile (only after the digests pass finishes normally) and verifies the checkout** (reclones rather than reusing a stale cache), so the AI rules stay fixed per project. A digests-only crash is `status: "partial"` / exit 4 (the official result stands; exit 3 is reserved for an official-pass crash).

- **Insight tools (drupal.org-aware, degrade gracefully):** `scripts/analysis/deps-status.sh` classifies each contrib dependency's D11 readiness against the drupal.org release-history feed (`ready`/`not-ready`/`not-on-drupalorg`/`unknown` — never guessed); `scripts/contrib/find-upstream-issue.sh` checks the issue queue for an existing D11 effort (best-effort title scan via the api-d7 feed, always with the filtered issue-queue URL as the reliable fallback); `scripts/analysis/explain-deprecations.sh` annotates analyzer output with what changed + the fix + a drupal.org change-records link, driven by the curated `config/deprecations.json` map (patterns are POSIX **ERE** — `grep -E` — so no PCRE lookarounds; the change-record link is a deterministic search URL keyed by the symbol, never a hardcoded node id). All three offer `--json` and never block a port on a blocked network. The same file holds `.signature_changes`, the catalog of D10→D11 breaking signature changes read by `scripts/analysis/scan-signature-changes.sh` (judged against `core_floor_from_requirement` of the declared range; shares the `php-scan.sh` class index/ancestry resolver with `check-port-safety.sh`) — add an entry only after verifying it in core source on every branch it names.

- **Port-safety gate (`scripts/analysis/check-port-safety.sh`, data in `config/port-checks.json`, PHP heuristics in `scripts/lib/php-scan.sh`):** deterministic, read-only checks run after every port/refactor batch (exit 3 = error findings, the stage is not done): DI interface vs `create()` resolved through the real ancestry under the Drupal root (verified fallback list only when a class cannot be parsed; never guess), removed-but-referenced `use`, `new self(` in `create()`, closures under Form/Render API callback keys, private/readonly properties in `DependencySerializationTrait` classes, `#[\Override]` while the core range spans D10, class-name case. Findings are attributed to the port via `git_port_base_ref` (the same base as `make-patch.sh --local`). `templates/rector.php.tmpl` (`drupilot-template-version: 3`; its `->withPhpSets()` argument is the `{{PHP_SET}}` token from `rector_php_set_arg`) skips the Rector rules behind these breakages (class_exists-filtered — Rector 2.x refuses unknown rule classes in `withSkip`); bump the version marker when the template changes in a way existing projects must receive, since `run-rector.sh` and `render-templates.sh` regenerate (after a backup) only drupilot-generated copies with an older marker; `phpstan.neon.tmpl`/`phpcs.xml.dist.tmpl` carry the same marker.

- **Plugin layout rule:** only `plugin.json` belongs in `.claude-plugin/`; all component directories (`commands/`, `agents/`, `skills/`, `hooks/`, `scripts/`, `templates/`) live at the plugin root. `marketplace.json` also sits in `.claude-plugin/` and resolves plugin `source` (`"./"`) relative to the repo root. Hook/command paths use the `"${CLAUDE_PLUGIN_ROOT}"`-prefixed form.

## Conventions when adding or editing

- **New shell script:** `#!/usr/bin/env bash`, then `set -euo pipefail` (hook scripts excepted — see above), source `common.sh` at the correct `../` depth, parse args with a `while/case` loop, gate heavy/destructive operations through `preflight.sh`, keep it idempotent (detect-and-skip), English messages only, and `chmod +x` it. Reuse the `common.sh` helpers (logging, config, prefs, `choose_one`, lock) rather than reinventing them; keep stdout parseable and add a `--json` mode when a command needs to read counts/data. **Portability: target bash ≥ 3.2 + BSD tools (stock macOS)** — no `${x,,}`/`${x^^}` (use `lc` from `common.sh`), no `declare -A`/`mapfile`/`local -n`/`declare -g`, no `sed -i` (use `sed_inplace FILE EXPR...`), no `readlink -f`/`realpath`/`grep -P`/`date -d`/`xargs -r`/`stat -c`/`find -printf`/`envsubst`, and expand a possibly-empty array as `${arr[@]+"${arr[@]}"}` (a bare `"${arr[@]}"` of an empty array is "unbound variable" under `set -u` before bash 4.4). The `portability` gate catches the greppable ones. Read DDEV add-ons with `ddev_addons_installed`/`ddev_addon_version` (they use `ddev add-on list --installed -j`), never the width-truncated human table. Watch the `set -e` traps: a function or pipeline whose last command returns non-zero (e.g. a `[[ ]] &&` tail, `grep -c` with no match) aborts the script — end such helpers with `return 0`. Reference the script's documented CLI from any command/skill that calls it.
- **New command:** `commands/<name>.md` with YAML frontmatter (`description`, `argument-hint`, `allowed-tools`; add `disable-model-invocation: true` for outward-facing/destructive commands like `drupilot-contribute`). Body is a prompt template that gates requirements, loads the relevant skill, drives scripts, and summarizes in English.
- **New decision point:** surface a consequential fork as a tab — add `AskUserQuestion` to the command's `allowed-tools`, make the recommendation the default option, persist the answer with `prefs_set` (`.drupilot.json`), gate outward-facing options on `autonomous=false`, and mirror the choice in the relevant skill/agent. The shell-side counterpart is `choose_one()`.
- **New skill/subagent:** `skills/<dir>/SKILL.md` / `agents/<name>.md` — embed the relevant versions/commands from `../PROMPT.md` §1–§3 so they never re-research.
- **Templates** (`templates/*.tmpl`) use `{{PLACEHOLDER}}` tokens substituted at setup time and are parameterized by the PHP target. Render them only through `render_template TPL DEST KEY=VAL...` (`common.sh`; literal, awk-based) — `scripts/env/render-templates.sh` (`--dry-run`/`--json`/`--force`, validates with `xmllint`/`php -l`, exit 3 on differs/invalid) for the setup configs — never with ad-hoc `sed` or model-side substitution. An XML template's comments must never contain `--`.

## Changelog and releases

Record **every notable change in `CHANGELOG.md`** under the `[Unreleased]` section as you make it (Keep a Changelog format: `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`). This is the running log of improvements — do not skip it.

On a release, keep the version in sync across three places: rename `[Unreleased]` to the new version with a date in `CHANGELOG.md`, bump `version` in `.claude-plugin/plugin.json` **and** the `drupilot` entry in `.claude-plugin/marketplace.json` to match, then tag the commit `vX.Y.Z` (the `CHANGELOG.md` compare/tag links assume those tags exist). Follow Semantic Versioning.
