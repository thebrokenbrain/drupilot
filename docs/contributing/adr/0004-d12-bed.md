# 0004 — The provisional D12 cell pins Rector 2.6.1 and coder 9, without drush

- **Status:** accepted
- **Date:** 2026-10-04
- **Decided by:** the 1.0 working session (R-AUTO-3), spike AR-42 (T-M2-16)

## Context

Drupal 12 is in pre-release. M2 needs a provisional toolchain cell `12` for
`config/toolchain-reference.json` v2 (AR-09, T-M2-10). M6 needs the facts
behind it: how a D12 bed is created and installed, and which 0.9 assumptions
break. The 0.9 code assumes D11 everywhere:

- `ddev-up.sh` creates a `drupal11` project and requires `drush/drush:^13`;
- the 0.9 reference set pins rector 2.5.2, phpstan 2.2.2 and coder 8.3.31;
- the `post-edit-lint.sh` hook is tuned to PHPCS 3 and coder 8.

X5 left the cell-12 Rector pin open. 2.6.1 was the candidate, because
core-dev 12 requires `phpstan ^2.2.14` and rector 2.5.2 is `known_broken`
with phpstan 2.2.16. 02-F5 found no stable drush for D12. AR-09 allows
`drush: null` once a drush-free site install has been verified. It named
`php core/scripts/drupal install` as the [U] candidate.

The pre-release used here is **12.0.0-beta1**. It is the newest 12.x in
`updates.drupal.org/release-history/drupal/current` (released 2026-09-30)
and on packagist p2 `drupal/core-recommended`. No beta2 or RC existed on
2026-10-04.

`rector_sets` and `rector_php_set` record what run R4 verified, not what a
T=12 port renders: the sets come from `rector_sets_for_plan` (T-M6-06), and
the PHP set from the floor L of the declared range (ADR 0002: `php85` only
when L is 8.5, as for `^12`; `php83` for `^11.3 || ^12`).

Three combinations go with it. rector `2.5.2` also crashes with phpstan
`2.2.14` and `2.2.15`, which ADR 0001's `known_broken` row (rector 2.5.2
with any phpstan from 2.2.6 on) already covers. The other three cannot even
be installed, so T-M2-10 records them in cell 12's note rather than in
`known_broken`, which lists sets that install and then crash (ADR 0015):

- `drush/drush` `^13` with `drupal/core` `12.*` (guzzle `^7`, symfony
  `^6 || ^7`);
- `drupal/coder` `8.3.31` with `drupal/core-dev` `12.*` (core-dev requires
  coder `^9.0`);
- `phpstan/phpstan` `2.2.2` with `drupal/core-dev` `12.*` (core-dev requires
  phpstan `^2.2.14`).

Mechanism, for M6:

- **Rector: 2.6.1.** It is the only usable choice. Rector 2.5.2 installs
  next to core-dev 12, because it requires `phpstan ^2.2.2`. It then crashes
  on start with every PHPStan that core-dev 12 allows (2.2.14, 2.2.15,
  2.2.16), and phpstan 2.2.2 cannot be installed next to core-dev 12.
  drupal-rector 1.1.3 still has `conflict rector/rector >=2.6.2`. PHPStan
  resolves to 2.2.16; Rector 2.6.1 also passed the smoke test with 2.2.14.
- **drush: `null`.** drush ^13 (13.8.0) does not install on 12.0.0-beta1.
  `14.x-dev` installs and works (`site:install`, `pm:install`, `us-a`), but
  only with two more dev branches as root requires, because the bed's
  `minimum-stability` is `beta`. Those branches are `grasmash/yaml-cli:4.x-dev`
  and `chi-teck/drupal-code-generator:4.x-dev`. That makes three unreleased
  commits per bed. A commit pin (`14.x-dev#d688132…`) works, but it is still
  not a release. Everything the bed needs from drush has a verified drush-free
  replacement, except `upgrade_status:analyze`.
- **Site install without drush: a PHP helper, not `dr install`.**
  - The 0.9 candidate `php core/scripts/drupal` fails fatally in a
    recommended-project layout. That shim is deprecated since 11.4 in favour
    of `dr`, and the `dr` script finds the autoloader only through
    `vendor/bin/dr`.
  - `vendor/bin/dr install` is unusable on DDEV.
    `InstallCommand::isDrupalInstalled()` treats any `$databases` entry as
    "installed". DDEV's `settings.ddev.php` always defines one, so the command
    exits 0 without doing anything on an empty database. With
    `IS_DDEV_PROJECT` unset, it installs into SQLite instead, and it appends
    that SQLite connection to `settings.php`, after the DDEV include.
  - The working path is a short PHP script that calls core's
    `install_drupal($class_loader, $settings)`, which is what drush does. It
    passes `interactive: FALSE`, the profile and the `install_configure_form`
    values. The settings form is skipped because DDEV's database settings
    verify.
  - The script stays in the plugin. `ddev exec` forwards stdin, so it runs as
    `ddev exec php -- <docroot> <profile> <name> <pass> < site-install.php`
    (the verified lab runs hardcoded `web` and passed only the last three).
    It must use `getcwd()`.
  - A reinstall must empty the database first (`ddev mysql -e 'DROP DATABASE
    db; CREATE DATABASE db;'`). Otherwise core throws
    `AlreadyInstalledException`.
  - Extensions are installed with `vendor/bin/dr ex:install <list> -y`. That
    is core's own CLI: it exists in 12.0.0-beta1 and on the 11.x branch, but
    not in 11.4.8. `dr cr`, `dr uli` and `dr status` cover the rest.
- **drupal/core from source on the bed.** The 12.0.0-beta1 dist of
  `drupal/core` ships **no `tests` directories**. Core's new
  `core/.gitattributes` export-ignores them (#3067979, committed 2026-09-23).
  So `BrowserTestBase`, `KernelTestBase` and the rest are missing:
  - PHPStan reports them as unknown classes;
  - PHPUnit cannot run a module test.

  `composer reinstall drupal/core --prefer-source` restores them; it took
  1m46s, and `web/core` grew to 410 MB with `.git`. A D12 bed therefore sets
  `preferred-install` to `source` for `drupal/core`.
- **PHPCS 4 / coder 9.0.1 works with `phpcs.xml.dist` and with the hook, with
  one behaviour change to fix:**
  - The rendered ruleset loads (160 sniffs) and gives the same totals as
    `Drupal,DrupalPractice`.
  - The hook's `--exclude` list is still accepted.
    `Drupal.Classes.UnusedUseStatement` no longer exists and is silently
    ignored; `SlevomatCodingStandard.Namespaces.UnusedUses` is the one that
    matters.
  - coder 9 reports an unused `use` as an **ERROR** (Slevomat's default),
    where coder 8.3.31 reported a warning. In Phase 1 the hook's phpcbf pass
    keeps the `use`, but its report pass now surfaces "Type X is not used in
    this file" as an error for the model to fix. The report pass needs the
    same Phase-1 exclusion as the phpcbf pass.
  - PHPCS 4 exit codes are bit flags: 1 fixable, 2 non-fixable, 4 failed to
    fix, 16 process error, 64 requirements not met. phpcbf now exits 0 after
    a full fix and 2 when non-fixable issues remain. drupilot only passes
    these codes through, or ignores them with `|| true`. The phpcbf comment
    in `run-phpcs.sh` still describes PHPCS 3.
  - PHPCompatibility is not part of any cell. 10.0.0-alpha2 accepts PHPCS
    `^3.13.3 || ^4.0`, and it installed and ran clean on PHPCS 4.0.4 with
    `testVersion 8.5-`.
- **upgrade_status 5.0.0-alpha3** installs on 12.0.0-beta1 (`^10.4 || ^11 ||
  ^12`).
  - `drush us-a` works with drush 14.x-dev, with the same `--format
    plain|checkstyle|codeclimate` as 4.x. The command exits 3 when it finds
    issues, which `ddev drush` turns into 1.
  - On a D12 bed it reports **Drupal 13** readiness: "removed from
    drupal:13.0.0", and a UI titled "Drupal 13 upgrade status". The X18
    next-major caveat therefore applies here too.
  - With `drush: null`, its CLI pass is skipped with a manifest note. The UI
    route (`/admin/reports/upgrade-status`, HTTP 200) is the only drush-free
    surface.

## Consequences

- **T-M2-10** writes the cell above with `verified: false` and adds the four
  `known_broken` rows.
  - With 0.9 code on this bed, `install-toolchain --dry-run` selects the 0.9
    reference set. phpstan 2.2.2 and coder 8.3.31 cannot resolve next to
    core-dev 12. Cell selection must therefore come from the target major,
    never from the 0.9 set.
  - Since cell 12 is unverified, `--source reference` on cell 12 warns and
    falls back to `range`, as AR-09 already says.
- **`ddev-up.sh` in M6:**
  - The project type comes from `config/targets/12.json` `ddev_type`
    (`drupal12`), not the hardcoded `drupal11` (L235).
  - The drush constraint comes from the cell (L246, and "Step 5", at
    L548–563 on `integration/1.0.0` after the 0.9.2 hotfix). With
    `drush: null`, Step 5 is skipped and recorded. The core-cache key, which
    `core_cache_lookup` matches on its drush field, uses `none`. Today a
    failed drush require is only a warning, so a 0.9 run on D12 continues
    without drush.
  - The locked-core regex (L268) must accept a pre-release such as
    `12.0.0-beta1`; today it drops it, and the core is resolved again.
  - Before the base-core cache is stored, the script sets
    `preferred-install` to `source` for `drupal/core` and installs core from
    source.
  - The "PHP 8.5 needs Drupal 11.3" logic (L278–291, and the "PHP 8.5 on
    the core this test-bed actually has" block at L646) and the
    "Drupal 11" wording become data-driven.
  - A bed health check probes `/user/login`, because D12's standard profile
    sets the front page to `/admin/welcome`, which returns 403 to anonymous
    users.
- **Site install** becomes a plugin-side helper (the `install_drupal()`
  script above, piped through `ddev exec php --`). It is used whenever the
  cell has `drush: null`.
  - `run-upgrade-status.sh` (L74–101), `drush twig:compile` (AR-08) and the
    `ddev drush site:install` hint in `skills/ddev-environment/SKILL.md` L369
    are skipped, or point to the helper, with a run-manifest note.
  - `vendor/bin/dr ex:install` replaces `drush en` on D12 only.
- **`post-edit-lint.sh`** (cell 12, before D12 is offered): exclude
  `SlevomatCodingStandard.Namespaces.UnusedUses` from the Phase-1 **report**
  pass too. `run-phpcs.sh`'s hardcoded `installed_paths` fallback is
  unchanged, but it would drop PHPCompatibility if it ever ran.
- **Templates / PHP data (AR-03):**
  - For T=12, `rector.php` renders the sets `rector_sets_for_plan` gives
    (R4 verified `DRUPAL_10`, `DRUPAL_11` and `DRUPAL_120` together) and the
    PHP set of the floor L (ADR 0002).
  - The `php_target_unconfirmed` fallback to `php84` is stale for Rector
    2.6.1.
  - `DRUPAL_120` holds one rule (`AddSymfonyConstraintValidatorTypeDeclarationsRector`),
    so D12 coverage still rests on PHPStan's "removed from drupal:12.0.0"
    deprecations.
- **Test adaptation (M6):** two new D12 detectors:
  - Kernel, Functional and FunctionalJavascript test classes must carry
    `#[RunTestsInSeparateProcesses]` (`KernelTestBase.php` L194,
    `BrowserTestBase.php` L305);
  - PHPUnit 12 ignores `@dataProvider` annotations.
- **Side finding (any cell, Rector work in M2):** `run-rector.sh` L527–528
  and L536 count every `^ \* …Rector$` line as an applied rule. That
  includes the FQCN listed under Rector's "This skipped rule is never
  registered" warning, so a skipped rule shows up in `rules` and
  `rule_hits`.
- **Re-verify at RC and at GA (T-M6-02):**
  - the pre-release tag;
  - core-dev's phpstan, coder and PHPUnit floors;
  - whether drush 14.0.0, or a 14 beta or RC within the bed's stability, is
    tagged on packagist. If so, the cell gets a drush pin;
  - whether `tests export-ignore` is still in the core dist;
  - whether `dr install` still ignores existing database settings;
  - whether `dr ex:install` is still there;
  - the drupal-rector `rector >=2.6.2` conflict and its D12 set coverage;
  - upgrade_status 5.x past alpha3;
  - newer coder 9.x and PHPCS 4.x releases, and Slevomat's UnusedUses
    severity;
  - the DDEV release and its `drupal12` type.
- **Not verified here:**
  - a D12 bed built by `ddev-up.sh` itself (its create step was not used);
  - `--apply` runs of Rector;
  - a full PHPUnit suite;
  - a drush-free run of the upgrade_status scan, which the UI starts as a
    batch;
  - whether `dr ex:install` ships in 11.5.0.
