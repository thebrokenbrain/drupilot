# Upgrading from 0.9 to 1.0

drupilot 1.0 keeps the 0.9 commands, flags, settings and tabs: contract tests freeze them, with the exit codes,
the generated names and the keys of `preflight.sh`, `port-summary.sh` (schema v1) and `core-strategy.sh` `--json`,
for all of 1.x. What changes is how drupilot decides and
records a port. There is no migration step: 1.0 reads a project 0.9 set up as it is, and each part of it moves
to 1.0 when the stage that owns it runs, as described below. Update the plugin (see
[Install](../getting-started/install.md#update)), start a new session, and run `/drupilot-setup` once on each
project you are porting: it regenerates the configs and plans the port. Only the toolchain waits for a refresh
you run yourself.

## What happens to an existing project

**drupilot's state.** It lives in drupilot's data directory (`DRUPILOT_HOME`, else
`$XDG_DATA_HOME/drupilot`, `~/.local/share/drupilot` by default), as it has since 0.9.1. State that 0.9.0 left
in Claude Code's plugin data directory is copied there once, by the first command that writes state.

**The lock.** A lock that 0.9 wrote keeps the Drupal core version it froze and 0.9's dev toolchain, until you
refresh it. `install-toolchain.sh` says so when it runs, and refreshing installs the current known-good set:

```bash
bash "$CLAUDE_PLUGIN_ROOT/scripts/env/install-toolchain.sh" --dir <drupal_root> --source reference
```

**Generated configs.** A `rector.php`, `phpstan.neon` or `phpcs.xml.dist` that drupilot generated from an older
template is regenerated when `/drupilot-setup` renders the configs (`/drupilot-refactor` renders `phpstan.neon`
only); `run-rector.sh` also regenerates an older `rector.php` itself. The previous file is kept in `<drupal_root>/.drupilot/backups/`. A
config you edited by hand after 1.0 rendered it is never overwritten.

**Assessments and test results.** 1.0 fingerprints a module's sources with Twig, JavaScript and CSS included, so
the test results (and a core matrix) 0.9 recorded show as stale once (`stale_reason: digest-algorithm`). A 0.9
assessment is read as it is and not flagged: run `/drupilot-assess` again (1.0 computes the verdict from its
findings), then `/drupilot-test`.

**The upgrade plan.** 1.0 plans before it acts: `/drupilot-setup` freezes a draft plan in the Drupal root's lock,
and `/drupilot-port` freezes the final one ([Upgrade paths](../concepts/upgrade-paths.md)). A project set up by
0.9 has no plan yet. The next setup or port computes one, and `bash "$CLAUDE_PLUGIN_ROOT/scripts/drupilot.sh" plan
show` prints it.

**Patch and test-bed names.** They are unchanged for Drupal 11: `MODULE-port-to-drupal-11.patch`, a loose
module's `<name>-d11` test-bed, a `drupal11` DDEV project.

## Renamed settings

A name 1.0 renamed keeps working for all of 1.x and is removed in 2.0.0. The full list, with what warns, is in
[Deprecations of drupilot](../reference/deprecations-of-drupilot.md). In short:

| 0.9 | 1.0 |
| --- | --- |
| `DRUPILOT_KEEP_D10=true` / `false` | `DRUPILOT_CORE_TARGET_STRATEGY=keep-previous` / `target-only` |
| strategy values `keep-d10`, `d11-only` | `keep-previous`, `target-only` (for Drupal 11 drupilot still writes the 0.9 names) |
| `make-issue.sh --d10-unverified` | `--prev-major-unverified` |

## What is new

- **The upgrade plan.** The target major, the declared core range, the PHP window, the Rector sets of every core
  minor on the way and the core removals are decided once, frozen in the lock, and read by every stage.
- **The PHP stage.** Every PHP of the window is checked: `php -l`, PHPCompatibility, the core polyfills, a narrow
  Rector compat pass, and a test leg on the lowest PHP ([PHP and the core target](../concepts/php-and-core-target.md)).
- **Core removals.** A module that still uses a module, theme or library core removed (Drupal 11.0's, or Drupal
  12's in the preview) gets a worklist item for a person.
- **Deterministic findings.** The tools' output becomes findings and a worklist with stable ids. The assessment's
  verdict is computed from them, the port manifest is generated, and a fixpoint gate checks that nothing
  automatic is left at the end of a port ([Determinism and replay](../concepts/determinism-and-replay.md)).
- **`--target N`** and the [Drupal 12 preview](../guides/d12-preview.md), experimental and off unless you opt in.
- New settings, such as `DRUPILOT_TARGET_MAJOR`, `DRUPILOT_ALLOW_PRERELEASE`, `DRUPILOT_FIXPOINT`,
  `DRUPILOT_LOCK_LOCATION` and `DRUPILOT_LENIENT_DEPS`: see [Configuration](../reference/configuration.md).

## Experimental in 1.0

These may still change in a 1.x release:

- the files 1.0 adds to the hidden state directory: the raw tool reports, `findings.json`, `worklist.json`,
  `actions.jsonl`, `fixpoint.json`, `stages.json`, `port-manifest.json` as 1.0 generates it (schema 1) and the
  run manifests under `runs/`;
- `assess.json` as 1.0's `assess.sh` writes it: its own schema 1 (`schemas/assess.schema.json`), which keeps few
  of 0.9's keys (the timestamp is now `meta.generated_at`), so read it as a new record; the upgrade plan in the
  lock, and the keys 1.0 adds to `last-test.json` and the lock;
- the Drupal 12 preview.

The contract tests freeze `port-summary.sh --json` (schema v1), the keys of `preflight.sh --json` and
`core-strategy.sh --json`, the exit codes and the generated names. 1.0 still reads the 0.9 records, and keeps the
0.9 keys of `state.json`, `last-test.json` and the lock, except the keys it moved under `meta` (the timestamps, and
`rector-rules.json`'s `subject`): see [Per-module state](../reference/state.md).

## If something goes wrong

- `/drupilot-doctor` checks your requirements and reports known pitfalls.
- `/drupilot-status` shows what drupilot recorded for a module, and the next step.
- A toolchain that does not work after the update: refresh it with `--source reference`, as above.
